4.1 Transaction and data boundaries

Core entities: user, role assignment, customer/contact/location, project, MSR version/scope/equipment, operational event, workflow task, approval, document/template/artwork version, signature request/event, payment/allocation, adjustment, payable, project cost, calculation snapshot, commission/report, ledger/period, inventory lot/movement/serial, asset/loan, configuration version, notification, integration outbox, and audit event.

Each state-changing command locks or checks the current entity version, authorizes the actor, validates transition guards, writes business changes plus audit/outbox atomically, and returns success only after commit. Duplicate submissions return the original result. Two competing approvals cannot create two current versions. External service calls occur outside database transactions and must reconcile uncertain results before retrying.

Project codes follow SPR Sprint 04 §7: SequentialNumber-Initials-YYYY-MM-DD, sequence starting at 101, creation date in America/New_York. A PostgreSQL sequence consumes numbers even on rollback; gaps are permitted, reuse is forbidden. Names and customer contact changes never mutate an approved project snapshot.

4.4 Security and audit

Every API, export, search, background job and download enforces role, record scope, field and action access. Sales Associates can maintain assigned drafts; Technicians see assigned installation details; AP sees only evidence needed for payable duties. Broad financial information is restricted to Sales Manager and Comptroller; Installation Manager gets only the authorized commission/contractor-payment and installation views. OD-07 now approves these minimum assigned-record scopes, including AP payable amounts and supporting evidence needed for its duties.

Business audit events are append-only and hash chained with canonical serialization, unique sequence, prior hash and current hash. Serialize concurrent chain appends; include actor, role at action time, UTC timestamp, entity/version, reason and controlled before/after values. Exclude passwords, tokens and unnecessary private data. Business mutation fails if its audit write fails. Export signed hash anchors to the protected archive so rewriting the database chain alone is detectable.

Use TLS for every hop and encryption at rest for database, objects, queues, backups and logs. IAM task roles retrieve only the necessary secrets at runtime. Rotate supported database credentials; provider OAuth/token rotation follows provider capabilities rather than a promise of arbitrary automatic rotation. Record secret references and rotation events, never secret values. Disallow routine application/admin permissions to delete protected records or disable retention; alert on key-deletion, retention-reduction or privileged-access attempts.

5.1 Backup and retention schedule

Enable RDS PITR with a proposed 35-day rolling recovery window, plus separate retained daily snapshots. Take the business end-of-day backup at 00:15 Eastern for the preceding day; record business date and backup completion timestamp. Daily retained backups include database, documents, templates/artwork, approved configuration, audit records/anchors, notification/integration history and a checksum manifest. Rolling PITR expiration does not delete business history or retained daily archives.

Business history is retained indefinitely with no authorized permanent-delete operation. Use S3 Object Lock, legal holds without an expiration date, restricted hold-removal permissions, compliance retention windows renewed before expiry, and protected backup vaults. Legal holds can be removed by sufficiently privileged identities; do not describe them as mathematically permanent protection. Preserve encryption-key availability and monitor retention settings. Drive permissions alone do not establish immutable retention. [T4]

Run the monthly restore test on the last Sunday at 03:00 America/New_York in an isolated environment. No live email/signature delivery occurs from restored data. Verify counts, relationships, signatures, file checksums, audit anchors, ledger balance, historical reports, role access and configuration versions. Store timings and evidence. Use a daily scheduled date check to identify the last Sunday. The stated time is outside the Eastern daylight-saving clock transition hour.

Infrastructure failover is preauthorized automation within the design; destructive restore or business-data reconciliation needs Comptroller incident authority. Measure recovery from actual service unavailability, not from when an operator starts restoring. Alert immediately, target technical intervention within 5 minutes, and reserve the remaining time for recovery and validation. A technical responder and backup owner are necessary; appointing the Comptroller as owner does not itself create 24-hour engineering coverage (OD-09).

6.3 Revision, holds, cancellation and reopening

Revision: a proposal records the changed fields, reason, evidence and impact. Copy the last approved MSR into a new numbered draft; never overwrite it. Revision states are DRAFT → SUBMITTED → APPROVED or REJECTED. Keep current approved version separate from pending draft. Changed-scope work is blocked immediately; this implementation pauses installation while commercial impact is reviewed. Rejection permits resumption only within the original approved scope.

Approval of a revision authorizes the new commercial version but does not authorize changed-scope installation by itself. Regenerate affected documents; supersede active requests while preserving originals; obtain new required signatures; recompute baseline and applicable rescission/deposit gates; resume only after all relevant checks pass. A refund or retrospective financial correction after completion does not automatically require re-signing completed physical work; it follows the adjustment process.

Hold: preserve the prior phase plus hold_reason, proposal/incident ID, approver and evidence. Holds include scope review, signature expiry, unresolved payment adjustment, document conflict and data-integrity failure. Clear only the specific resolved hold; never bypass other guards. A routine exception cannot waive legal rescission controls or immutable-history rules.

Cancellation: Sales Manager, Installation Manager or Comptroller may request it; Sales Manager or Comptroller authorizes execution under BL R-012. Stop future work and active unsigned requests; preserve deposits, signatures, costs and obligations. Refunds/fees follow their own approval rules. Project code remains permanently reserved. Reopen: authorization and reason are mandatory; retain same identity/code, create revision or correction records as appropriate, and reevaluate all affected gates. Completed/closed financial snapshots and earned commissions remain preserved; invalidated eligibility creates adjustments, never a second unlinked payment.
