GECC Minimum Viable Product Foundation Implementation Slice — MVP v1.0 Purpose: Deliver the smallest usable GECC system that establishes controlled project records, approval governance, version history, auditability, and basic contract/invoice generation. MVP status: Proposed implementation baseline Related baseline: GECC Requirements Baseline v1.0 Target implementation: Sprints 01–07 ________________________________________ 1. MVP objective The MVP shall allow GECC to: 1. Create authorized users. 2. Manage customers and project locations. 3. Create and maintain draft Master Sales Records. 4. Submit records for approval. 5. Approve or reject commercial project records. 6. Preserve approved versions. 7. Generate a basic contract and invoice from an approved version. 8. Record all material activity in an audit trail. The MVP shall establish the system of record before installation, payment, commission, inventory, and financial-reporting features are introduced. ________________________________________ 2. MVP scope Included • User authentication. • Role-based permissions. • Customer records. • Customer contacts. • Project records. • Project locations. • Master Sales Record. • Draft and submitted states. • Approval and rejection workflow. • Immutable approved versions. • Controlled revision workflow. • Audit logging. • Basic contract generation. • Basic invoice generation. • Document-version references. • Search and basic record filtering. • MVP acceptance testing. Excluded from MVP The following are reserved for later implementation: • Electronic signatures. • Installation scheduling. • Three-day waiting-period enforcement. • Completion certificates. • Payment verification. • Accounts receivable and accounts payable processing. • Commissions and fixed compensation. • Inventory and FIFO valuation. • Fixed assets and depreciation. • Loans. • Financial-period closing. • Dashboards and notifications beyond basic workflow messages. • Data migration from legacy spreadsheets. • Advanced reporting. • External banking integrations. ________________________________________ 3. MVP user roles Role MVP permissions Sales Associate Create and edit customers, contacts, projects, and draft Master Sales Records; submit records for approval; view records they are permitted to access. Sales Manager View assigned records; approve or reject Master Sales Records; request corrections; generate documents from approved versions. Comptroller View all records; approve or reject Master Sales Records; approve commercial revisions; generate documents; review audit history. Installation Manager View approved project and installation-related information only. No commercial approval authority in the MVP. Technician No active MVP editing permissions. May be added in the installation slice. Accounts Payable Associate No active MVP permissions. Database Administrator Manage technical configuration and user access; cannot alter business records without a recorded administrative action. System Administrator Manage roles and system configuration; all privileged actions are audited. 3.1 Permission principles • Access is granted by role, not by informal user identity. • Users may only perform actions permitted by their role. • Approval cannot be performed by the person who prepared the record where separation of duties is required. • Approved commercial information cannot be edited directly. • Administrative access does not bypass audit logging. • Deleted business records are not physically removed; they are archived or marked inactive. ________________________________________ 4. MVP project states The MVP shall support the following states: 1. Draft — Record is being prepared. 2. Submitted for approval — Record is awaiting Sales Manager or Comptroller review. 3. Rejected — Record requires correction before resubmission. 4. Approved — Commercial version is approved and locked. 5. Revised — A new draft version is being prepared from an approved version. 6. Cancelled — Project is no longer active and cannot reuse its project code. The MVP shall not mark a project as Completed, because payment verification and completion-certificate functionality are outside the first implementation slice. ________________________________________ 6. Master Sales Record workflow 6.1 Create draft 1. Sales Associate creates or selects a customer. 2. Sales Associate creates a project. 3. The system generates a unique project code. 4. The Sales Associate completes the draft Master Sales Record. 5. The system validates required fields. 6. The record remains in Draft status until submitted. 6.2 Submit for approval 1. Sales Associate submits the completed record. 2. The system validates: • Customer information. • Project location. • Scope. • Pricing. • Payment terms. • Required equipment and materials data. 3. The system records the submission event. 4. The record changes to Submitted for approval. 5. Commercial fields become unavailable for ordinary editing. 6.3 Approve 1. Sales Manager or Comptroller reviews the record. 2. The approver may: • Approve the record. • Reject the record. • Request correction. 3. Approval requires: • Approver identity. • Approval timestamp. • Approved version number. • Optional approval note. 4. The record changes to Approved. 5. The approved version becomes immutable. 6. Contract and invoice generation becomes available. 6.4 Reject 1. The approver selects Reject. 2. A rejection reason is required. 3. The system records the rejection event. 4. The record changes to Rejected. 5. The Sales Associate may correct and resubmit it. 6. The rejection history remains permanently available. 6.5 Revise an approved record 1. An authorized user selects Create Revision. 2. The system copies the approved version into a new draft version. 3. The prior approved version remains locked. 4. The revision requires: • Revision reason. • New version number. • Updated fields. • New approval. 5. The revised version cannot replace the prior version until approved. ________________________________________ 7. Versioning requirements Each Master Sales Record shall have: • A project identifier. • A sequential version number. • A version status. • A creation timestamp. • A creating user. • A source version, where applicable. • A revision reason. • An approval decision. • An approval timestamp. • An approver. 7.1 Version rules • The first draft is Version 1.0. • Approval locks the version. • A commercial revision creates Version 2.0, Version 3.0, and so on. • Approved versions cannot be deleted. • A rejected draft may be corrected or replaced, but the rejection remains recorded. • Documents identify the version from which they were generated. • The system displays the current approved version separately from draft revisions. ________________________________________ 8. Audit logging The MVP shall record an audit event for every material business action. 9.1 Required audit fields Field Description Audit event ID Unique event identifier Event type Creation, edit, submission, approval, rejection, revision, cancellation, login, document generation, or access User ID User performing the action Role at time of action User’s role when the event occurred Timestamp Date and time in the system timezone Entity type Customer, project, Master Sales Record, user, or document Entity ID Affected record Version ID Applicable record version Previous value Prior value where relevant New value New value where relevant Reason Required for rejection, revision, cancellation, or administrative action Source User interface, system process, or administrative process 9.2 MVP audit events The MVP shall audit: • User creation. • User activation and deactivation. • Login success and failure. • Customer creation and edits. • Project creation and edits. • Master Sales Record creation. • Field changes to draft records. • Submission for approval. • Approval. • Rejection. • Revision creation. • Project cancellation. • Document generation. • Record viewing where restricted access applies. • Permission changes. • Administrative actions. Audit records shall be append-only. Users shall not be able to edit or delete audit entries through the normal interface. ________________________________________ 10. Basic contract generation The MVP contract generator shall use an approved template and populate: • Customer name. • Customer billing address. • Project address. • Project code. • Scope of work. • Equipment and materials summary. • Contract price. • Discounts and taxes. • Payment terms. • Master Sales Record version. • Generation date. • Customer signature placeholder. • Authorized GECC signature placeholder. The generated contract shall: • Be available only after Master Sales Record approval. • Include the source version number. • Be stored against the project. • Be assigned a document ID. • Be reproducible from the same approved version. • Record the generation event in the audit log. Electronic signatures are not part of this MVP. The document shall contain signature placeholders for the later signature workflow. ________________________________________ 11. Basic invoice generation The MVP invoice generator shall use an approved template and populate: • Invoice number. • Project code. • Customer name and billing address. • Project address. • Invoice date. • Line-item description. • Quantity. • Unit price. • Discount. • Tax. • Total amount. • Payment terms. • Master Sales Record version. • Customer signature placeholder. • Authorized GECC signature placeholder. The invoice shall: • Be generated only from an approved Master Sales Record. • Match the approved commercial values. • Record the source version. • Be stored against the project. • Be assigned a document ID. • Generate an audit event. • Prevent manual modification of calculated totals within the generated document. Payment processing and payment verification are excluded from the MVP. ________________________________________ 12. MVP acceptance criteria The MVP is accepted when all of the following tests pass: Users and permissions • A user can log in only when active. • A Sales Associate cannot approve a Master Sales Record. • An Installation Manager cannot approve commercial terms. • A Sales Manager and Comptroller can approve records. • Permission changes are audited. • Deactivated users cannot perform business actions. Customers and projects • A Sales Associate can create a customer and contact. • A project can be linked to one customer. • A project receives a unique project code. • The system warns about likely duplicate customers or locations. • A cancelled project code cannot be reused. Master Sales Record • A draft record can be created and saved. • Required fields are validated before submission. • A submitted record cannot be edited through ordinary draft controls. • A rejected record can be corrected and resubmitted. • An approved record displays its version number and approval information. Versioning • Approval locks the approved version. • A commercial change creates a new version. • The previous version remains viewable. • The system records the revision reason. • Documents identify their source version. Approval workflow • Only the Sales Manager or Comptroller can approve. • Approval records the approver and timestamp. • Rejection requires a reason. • An unapproved record cannot generate a contract or invoice. • Approval and rejection events appear in the audit history. Audit logging • Required create, edit, submit, approve, reject, revise, cancel, and document-generation events are recorded. • Audit events identify the user, timestamp, entity, action, and affected version. • Ordinary users cannot edit or delete audit events. Contract and invoice generation • A contract can be generated from an approved record. • An invoice can be generated from an approved record. • Generated values match the approved version. • Each document includes the project code and source version. • Each generated document is stored and auditable. • Draft or rejected records cannot generate final documents. ________________________________________ 13. MVP implementation sequence Step Deliverable Primary owner 1 Database schema for users, customers, projects, versions, approvals, documents, and audit events Database Administrator 2 Authentication and role-based permissions Database Administrator 3 Customer, contact, and project screens Development team 4 Master Sales Record draft and validation screens Development team 5 Versioning and approved-record locking Development team 6 Approval and rejection workflow Sales Manager and Comptroller 7 Audit-event implementation Database Administrator and Development team 8 Contract and invoice templates Sales Manager and Comptroller 9 Document generation and storage Development team 10 MVP acceptance testing and sign-off GECC Business Owner ________________________________________ 14. MVP completion definition The MVP is complete when: • All MVP acceptance criteria pass. • Role permissions are approved. • The Master Sales Record versioning model is approved. • Contract and invoice templates are approved. • Audit events are visible and complete. • No approved commercial record can be silently overwritten. • Generated documents match approved source data. • The business owner approves the release for operational use. The next implementation slice after this MVP should add electronic signatures, installation workflow, the three-day waiting-period rule, completion certificates, and payment verification.
